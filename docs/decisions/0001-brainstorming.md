# ADR 0001: Architecture Brainstorming — Team Second Brain + GitHub Projects v2

## 1. Goal, Success Criterion, and the "Why"

### Goal (in plain words)
Build a **public, MIT-licensed, domain-generic GitHub template repository (`ORG/REPO`)** that gives a 5-to-15 person engineering team a working task board (**GitHub Projects v2**) and a structured Markdown knowledge base (**Second Brain**) inside a single GitHub organization—set up in **under 1 hour**, usable on **GitHub Free or Team**, with **zero external servers** and **zero preview-feature dependencies**.

### The "Why" (Intent, Human Constraints, and Anti-Goals)
Small teams starting from zero tools fail at project tracking and documentation for two predictable reasons: **tool fragmentation** (tasks in one SaaS app, docs in another, code in a third) and **update friction** (requiring 10 form fields to log a quick task, or forcing non-git users to open branches and pull requests just to close a card).

This design is shaped around four human realities:
1. **Browser & mobile first (asymmetric git usage):** Only 1–2 team members ("Alex", the knowledge writer) use `git` or Obsidian. The other 3–13 members ("Sam", working from a browser or mobile phone) interact **only** through the GitHub web UI or iOS/Android app. Filing a card must take **< 1 minute on a phone**, and capturing lessons learned at task completion must never require `git`, a terminal, or editing repo files by hand.
2. **Safe AI agent collaboration, human authority:** Coding and assistant agents (connected via the GitHub MCP server or API) take routine busywork off humans—filing cards, moving `Status` among `Todo` / `Doing` / `Blocked`, enriching fields, and drafting weekly summaries—while **only humans** may assign owners (`Assignees`), move cards to `Done`, or mark knowledge pages as `status: verified` / `last_verified`.
3. **Closed loop between doing work and remembering it:** Tasks are not truly `Done` until durable operational learnings are either linked (`Knowledge link` field) or captured in an issue comment that automation funnels into `inbox/` for the knowledge writer's consolidated review PR.
4. **Anti-goals (what makes this a failure even if it technically runs):**
   - Relying on non-existent GitHub Actions triggers (`on: projects_v2_item`, F1) or unverified public-preview features (`issue-intents` F15, Issue Artifacts F16, multi-select F17) as core guardrails.
   - Burning through GitHub Free's 2,000 Actions minutes/month with 24/7 high-frequency cron loops on a private repo.
   - Committing noisy state files to `main` on every poll or spamming engineers with repetitive bot comments until they mute notifications.
   - Building brittle automation with field names hardcoded across five YAML files that a 5-person team will abandon.

### Success Criterion (2-Week Pilot)
The template succeeds if a 5-person team runs it for 10 business days and achieves all three checks:
1. **≥ 90% board coverage:** At least 90% of real work done by the team is represented as issue cards on the board (no shadow spreadsheets or untracked side-work).
2. **100% blocker accountability:** Every card in `Blocked` has a human owner (`Assignees`), a `Blocked since` date, and a `Blocked reason` (`status:Blocked (no:assignee OR no:"Blocked since" OR no:"Blocked reason")` returns `0` items).
3. **≤ 10-minute stand-up from one dashboard:** Daily stand-up (or weekly review) completes in 10 minutes or less using **only** the project dashboard views (0–3m Blockers → 3–7m Doing by person → 7–10m Done & knowledge capture).

## 2. Overall Architecture Approaches Considered

Because GitHub Actions has **no native `projects_v2_item` trigger** (F1) and `GITHUB_TOKEN` **cannot read or write Projects v2** (F2), there are three genuinely different ways to architect the system:

| Dimension | Approach A: GitHub-Native Minimal (Built-in Workflows + Weekday Scheduled Poll & Issue Events) | Approach B: Reactive Webhook App (Org `projects_v2_item` Webhook → External Relay → `repository_dispatch`) | Approach C: Convention-First, Near-Zero Automation (Built-in Workflows + Saved Filter Views Only) |
|---|---|---|---|
| **How it works** | Uses Projects v2 built-in workflows for instant status basics (auto-add `is:issue is:open`, new item → `Todo`, 30d auto-archive) + `on: issues` Action triggers for instant assignee/close checks + **weekday business-hours GraphQL poll** using one shared script (`scripts/project_query.sh`) to stamp `Blocked since`, audit human-only `Done`, and collect `Learned:` comments into `inbox/`. | Deploys an external webhook receiver (e.g., Cloudflare Worker or AWS Lambda) subscribed to org-level `projects_v2_item` webhook events. On any board column drag or field change, the relay validates the actor or fires `repository_dispatch` into GitHub Actions for immediate reaction. | Uses **zero** scheduled Actions and **zero** org tokens. Relies strictly on built-in project workflows, field default values (F11), and saved dashboard filter views (`Needs Attention` view filtering `status:Blocked no:"Blocked since"`). Humans fill dates manually and catch violations in stand-up. |
| **Setup & Ops Footprint** | **< 1 hour**, 100% inside GitHub (`ORG/REPO` + Project v2 + 1 App or bot PAT). Zero external servers. | **2–4 hours**, requires provisioning, securing, monitoring, and paying for an external serverless endpoint + webhook secrets. | **~20 minutes**, zero secrets or tokens to rotate, nothing can break or expire. |
| **Reaction Latency** | **Instant** on issue events (`assigned`, `closed`, `labeled`); **0–60 min** (weekday business hours) on board column drags. | **Real-time (< 5 sec)** on all board column drags and custom field edits; exact webhook `sender.login` attribution. | **Manual** (waits until the next human stand-up or triage pass). |
| **Free-Plan Actions Cost** | **~332–574 billed min/month** on private repos (16–29% of GitHub Free's 2,000 min quota; 0 billed min if public). | **~150–300 billed min/month** (runs only when cards actually move on the board, plus external worker invocation cost). | **~30 min/month** (only runs knowledge frontmatter CI on PRs). |
| **Failure Mode at 5→15 Scale** | Small blind window if a card enters and leaves `Blocked` between polls (mitigated by `status:blocked` label trigger). | External relay becomes an unmaintained single point of failure; when webhook/cloud auth breaks, all board automation dies. | High human friction: engineers on mobile forget to stamp `Blocked since`, non-git users skip `inbox/` notes, and agent `Done` violations slip through. |

### Chosen Overall Design: **Approach A (GitHub-Native Minimal)**
**Why:**
1. **Fits the 1-hour, zero-infrastructure constraint:** Everything lives in the template repository and native GitHub Projects v2—no external cloud accounts or webhook relays to deploy or maintain (ruling out Approach B).
2. **Protects low friction for non-git users:** Automation handles the bookkeeping that humans forget on mobile (`Blocked since` stamping, extracting `Learned:` issue comments into `inbox/` PRs, weekly digest generation, and flagging unowned blockers), which pure convention (Approach C) fails to sustain past week 1.
3. **Graceful degradation:** Because every automated check is backed by a saved dashboard filter view (`Stand-up Dashboard` and `Needs Attention`), the board remains 100% usable even if Actions minutes run out or a token expires.

## 3. Challenging Every Assumption in the Brief

| # | Brief Assumption | Challenge / Reality Check | Architectural Mitigation in Our Design |
|---|---|---|---|
| **A1** | **Non-git users can capture knowledge via a comment OR a 2-line `inbox/` note in the GitHub web editor.** | Even the GitHub web file editor (*Add file → Create new file → Commit / Open PR*) exposes git branches and PR screens, which is clumsy on a mobile phone and intimidates non-git users. | Make **an issue comment prefixed with `Learned:`** (or applying label `needs-second-brain` + filling the `Knowledge link` field) the **primary DoD path** for non-git users. The scheduled workflow extracts `Learned:` comments from newly `Done` issues into `inbox/` files in one consolidated PR for the knowledge writers. |
| **A2** | **A single board and 10-minute stand-up scales smoothly from 5 to ~15 people.** | At 5 people (~8 `Doing` cards), scanning every person takes 4 minutes. At 15 people (~25–30 `Doing` cards), reading every card takes > 15 minutes. Also, GitHub Free allows only **1 auto-add workflow** per project (F4), which breaks if a 15-person org splits work across 3–4 repos. | Structure the 10-minute stand-up to walk **by exception** (1. Blockers oldest-first → 2. Doing cards breaching soft WIP `>2`, stale `>5d`, or waiting on agent review → 3. Newly Done missing `Knowledge link`). Include a lightweight `Area` single-select field (`area-a`, `area-b`, `ops`) for sub-team filtering at 15 people, and ship an optional Actions `auto-add` fallback for multi-repo Free-plan orgs. |
| **A3** | **Scheduled GraphQL polling replaces the missing `projects_v2_item` trigger (F1).** | On private repos, each Actions run rounds up to **1 billed minute**. A 24/7 15-minute cron (`*/15 * * * *`) runs ~2,880 times/month = **~2,880+ min/month**, exceeding GitHub Free's entire 2,000-minute monthly allowance (F13). | Default the consolidated `board-keeper` poll to **hourly during weekday working hours** (`0 8-18 * * 1-5` = ~242 runs/month ≈ 332 total min/month; or `*/30` = ~574 min/month), and fold blocker stamping, guardrail checks, aging alerts, digest, and comment extraction into one workflow. |
| **A4** | **A GitHub App or fine-grained PAT authenticates project automation reliably (F2).** | Fine-grained PATs expire (30–365 days) and break silently when they expire or when the creator leaves the org. GitHub App installation tokens expire after 1 hour—ideal for Actions (`actions/create-github-app-token`), but static MCP configs often use a PAT. | Recommend a **GitHub App** (`actions/create-github-app-token`) for GitHub Actions (org-owned, short-lived per-run token, clear `*[bot]` identity) and a **dedicated bot machine-user Fine-Grained PAT** for MCP agents (and as a 5-min Actions fallback). Add an `if: failure()` step using `GITHUB_TOKEN` to open an alert issue if auth fails. |
| **A5** | **Scheduled workflows (`schedule:`) keep running indefinitely once enabled.** | GitHub **automatically disables scheduled workflows after 60 days of repository inactivity** on public repos. If a team only interacts with Issues and Projects v2, git commit activity could hit zero for 60 days. | Keeping the **Second Brain (`knowledge/`, `inbox/`, `decisions/`) in the same repository** plus the `bot/inbox-capture` PRs produces regular commits that reset the 60-day clock without polluting `main` with snapshot commits. In addition, all scheduled workflows include `workflow_dispatch:` and `on: issues` triggers. |
| **A6** | **GraphQL polling can tell *who* moved a card to `Done`.** | Projects v2 GraphQL returns the *current* `Status` value of an item, not a complete per-field transition history with actor attribution for every past change. | Combine three layers: (1) Turn **OFF** built-in "Item closed → Done" so bots closing issues cannot trigger `Done`, (2) Trigger `on: issues: [assigned, closed, labeled]` where `github.actor` is 100% exact, and (3) Have the poll inspect the item's `fieldValueByName(name: "Status").creator.login` (which records who set the current field value in GraphQL) and compare against the poll state stored in the weekly digest issue body (`<!-- board-keeper:snapshot:{...} -->`). |
| **A7** | **A 5-person team will maintain custom Actions workflows and setup scripts.** | Small teams abandon custom automation if field IDs or option strings (`Blocked`, `Blocked since`) are scattered across multiple YAML files and bash scripts. | Define all fields and options in **one file (`project/fields.yml`)** and put all GraphQL queries/mutations in **one shared script (`scripts/project_query.sh`)** invoked by one workflow (`.github/workflows/board-keeper.yml`). Use `gh`, `jq`, and `yq` pre-installed on `ubuntu-latest`. |
| **A8** | **CODEOWNERS and branch rulesets protect `standards/` and `decisions/` on all plans.** | On **private** repositories, CODEOWNERS, required reviewers, and branch rulesets require **GitHub Team ($4/user/month)** and do not enforce on GitHub Free (F13). | Ship `.github/CODEOWNERS.example` for Team orgs, **and** enforce frontmatter schema, `locked: true` page protection, and "bots never modify `last_verified` or `status: verified`" inside `.github/workflows/validate-knowledge.yml`, which executes on **both Free and Team**. |

| **8. Blank issues in `.github/ISSUE_TEMPLATE/config.yml`** *(Brief §6)* | **A.** `blank_issues_enabled: true` (ON) + 4 ultra-lean YAML forms (`task.yml`, `bug.yml`, `blocker.yml`, `decision.yml`, each ≤ 5 inputs, 1–2 required).<br>**B.** `blank_issues_enabled: false` (OFF), forcing all issues through the 4 forms.<br>**C.** Blank issues only (no YAML issue forms). | **A:** Gives structured prompts for 95% of cards while allowing a 15-second title-only capture on mobile when someone is in a rush.<br>**B:** Enforces template structure 100%; creates friction on mobile when an item doesn't fit neatly or needs instant capture.<br>**C:** Fastest capture; loses structured prompts for Blockers and Decisions (ADRs). | **Pick A (`blank_issues_enabled: true` alongside the 4 lean YAML forms).**<br>*Reason:* Satisfies the "< 1 minute on a phone" rule for rapid capture while providing structured, low-friction forms (≤ 5 fields) as the default picker. |

## 5. YAGNI List (What We Deliberately Do NOT Build)

1. **No external servers, webhook relays, or custom web UIs:** Zero Cloudflare Workers, AWS Lambdas, databases, or custom frontends. Everything runs natively on GitHub Issues, Projects v2, and GitHub Actions.
2. **No public-preview features in the core template (Brief §5.3):**
   - **No Issue Artifacts (`gh issue artifact`, F16)** in core scripts or DoD rules.
   - **No Agent Automation Controls (`issue-intents` / `copilot_issue_intents`, F15)**—GitHub explicitly documents these as a workflow convenience, not a security control.
   - **No Multi-select fields (F17)** or **Organization-level Issue Fields (F10)** in core setup scripts.
   - *(All preview features are quarantined inside `docs/optional/experimental.md`.)*
3. **No Sprint / Iteration fields, story points / Effort math, or Roadmap views:** A 5–15 person Kanban team manages flow via soft WIP limits (`Doing ≤ 2` per person) and blocker escalation, not sprint velocity accounting or Gantt charts.
4. **No Pull Requests on the Kanban board:** Built-in auto-add uses `is:issue is:open` only. PRs link to issues via native `Development` / `Closes #N` references without cluttering columns or doubling WIP counts.
5. **No duplicate project-field dropdowns inside YAML Issue Forms:** Issue forms capture only the core text/context (1–2 required inputs, ≤ 5 total) and never duplicate `Priority`, `Status`, or `Area` dropdowns that belong on the Project v2 item.
6. **No Organization-level Issue Types dependency:** The template uses standard repository labels (`type:task`, `type:bug`, `type:blocker`, `type:decision`, `status:blocked`, `escalated`, `needs-second-brain`, `agent-drafted`, `policy-violation`) managed idempotently by `scripts/sync-labels.sh` so it works without org-admin Issue Type setup.
7. **No full LLM nightly compiler or static-site generator in this repository:** Per Brief §3 & §5.13, we ship the Second Brain folder skeleton (`inbox/`, `knowledge/area-a/`, `decisions/`, `standards/`, `_meta/`, `_templates/`), frontmatter schema (`_meta/schema.yaml`), `validate-knowledge` CI check, and deterministic `Learned:` comment-to-`inbox/` collector; the external LLM compiler, Quartz 5 static site, and SSO Q&A bot are documented as architectural integration points only.
8. **No local Kanzo or Obsidian Kanban board configs:** Evaluated in `docs/research.md` and excluded from the team architecture due to single-user SQLite conflict semantics and lack of multi-user RBAC (F18).

## 6. Open Questions and Chosen Defaults

*(Full details and switch instructions are recorded in [ADR 0003: Open Questions and Chosen Defaults](0003-open-questions.md).)*

| # | Open Question | Chosen Default | Alternative & How a Team Can Change It |
|---|---|---|---|
| **Q1** | **Should the guardrail workflow automatically revert agent `Done` / assignment actions, or comment + label + log in digest?** | **`auto_revert: false` (Visible comment + `policy-violation` label + weekly digest entry by default).** | Set `auto_revert: true` in `project/fields.yml` (or `AUTO_REVERT=true`) to make `board-keeper.yml` automatically revert bot-set `Done` transitions back to `Doing` and remove bot-added human assignees. |
| **Q2** | **What polling schedule balances responsiveness against GitHub Free's 2,000 Actions minutes/month?** | **`0 8-18 * * 1-5` (hourly, Mon–Fri 08:00–18:00 UTC) ≈ 242 cron runs/month (~332 total min/mo).** | Edit the `cron:` line in `.github/workflows/board-keeper.yml` to `*/30 8-18 * * 1-5` (~574 min/mo) or `*/15 * * * *` if running in a public repo. |
| **Q3** | **Where should poll state be stored so we do not commit noisy snapshot files to `main`?** | **Embedded inside the weekly digest issue body (`<!-- board-keeper:snapshot:{...} -->`) + GraphQL `Status.creator.login`.** | Zero git commit noise on `main`; optionally cache via `actions/cache` if desired. |
| **Q4** | **How do non-git users mark a card's takeaway for automatic extraction into `inbox/`?** | **Post an issue comment starting with `Learned:` (or `Decision:` / `Knowledge:`) before/when moving to `Done`.** | Teams comfortable with the GitHub web editor can also create a file in `inbox/` using `_templates/inbox-note.md`. |
| **Q5** | **What are the exact aging thresholds and anti-spam rules?** | **Blocked ≥ 3 days = reminder comment; Blocked ≥ 5 days = `escalated` label + mention `@ORG/maintainers`; Doing stale ≥ 5 days = check-in. Max 1 alert per 3 days.** | Configurable in `project/fields.yml` (`blocked_warn_days`, `blocked_escalate_days`, `doing_stale_days`, `alert_cooldown_days`). |
| **Q6** | **Which dashboard views are provisioned by default?** | **3 views:** `1. Board` (Kanban by `Status`), `2. Stand-up Dashboard` (Table: Blockers, Doing, Done last 7d), and `3. Needs Attention` (Table: hygiene exceptions). | Teams wanting 2 views can delete `3. Needs Attention`; teams scaling to 15 people can group `1. Board` by `Assignees` or `Area`. |
| **Q7** | **After how many days in `Done` should cards be auto-archived by the built-in workflow?** | **30 days (`status:Done updated:<@today-30d`).** | Preserves 30 days of Insights history (F7); adjustable to 14–90 days in Project Workflows UI. |
